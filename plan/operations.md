# 毎日の運用手順（定期タスク用）

関連: [[strategy]] / [[article-guide]]

定期タスクは、このファイルの手順で動く。1回の実行で記事を最大1本作る。

## 0. 前提の確認
- 作業場所: `C:\Users\Administrator\Projects\play\pocket-log`
- `CLAUDE.md`・`plan/strategy.md`・`plan/article-guide.md`・`topics.txt` を読む。
- `git pull` して最新にする。

## 1. 記事の種類を決める

| 種類 | 体験が要るか | 自動公開 |
|---|---|---|
| 調べもの型（制度・仕組み・考え方・旬ネタの解説。出典つき） | 要らない | する |
| あるある解決型（ルールや手順の提案） | 要らない（体験を主張しない） | する |
| やってみた型・買ってみた型 | 要る | しない（下書きで残し、ユーザーに体験の記入を頼む） |

- 体験が必要な記事は、体験を捏造しない。`【体験メモ：…】` の欄を残し、`draft: true` のままにする。
- 自動公開してよい記事は、「私は〜した」「試したら〜だった」のような体験の主張を書かない。

## 2. ネタを決める
- `topics.txt` の先頭から選ぶ。尽きていたら、WebSearch で最近の話題（物価、家計、節約、小さな贅沢、季節の行事）を調べて補充する。
- 数字・制度・商品名・価格は、出典を確認できたものだけ書く。出典のURLを本文に入れ、調べた日付を書く。
- 同じテーマの記事が既にあれば、重ならない切り口にする。

## 3. 書く
- `python new_post.py <slug> "<タイトル>" <公開日>` で雛形を作る。
- [[article-guide]] の基準で書く（友達のLINEの温度。見出しは答え。1段落3行まで）。
- アフィリエイトリンクを入れる場合は `pr: true`（ASP登録前は入れない）。

## 4. 推敲と検査（毎回必須）
1. **yomiyasu スキルで推敲する**。記事の種類は article。最終稿は `_work/` に置き、`yomiyasu_check.py run` と `verify` を実行する（作業フォルダの外のファイルは読めない）。
2. `python check.py` でエラーが0件であること。
3. `python build.py` が通ること。
4. 意味が変わっていないか、体験の捏造がないか、数字の出典があるかを自分で読み直す。

## 5. 公開の判断
- 自動公開してよい記事で、手順4がすべて通ったときだけ `draft: true` を外し、`date` を今日か翌日以降にする。
- 通らないとき、または体験が必要な記事は、`draft: true` のまま残す。
- 公開するときは `git add` → `git commit` → `git push`。GitHub Actions が毎朝6時にもビルドするので、`date` を明日以降にしておけば予約公開になる。
- 公開後、サイトのURL（https://pocketlog-note.github.io/pocket-log/）で表示を確認する。

## 6. 記録
- `topics.txt` から使ったネタを外す。
- `plan/log.md` に、日付・記事・公開か下書きか・次回への申し送りを1〜3行で追記する。
- 完了報告は、「何をしたか／確認できたこと／未確認のこと」を分けて書く。ユーザーの作業が必要な記事（体験メモの記入）があれば、最初に書く。

## 7. やってはいけないこと
- 体験の捏造。
- 出典のない数字・価格・制度の記載。
- yomiyasu を通さない公開。
- 本名・個人メール・個人情報の記載。
- アカウント作成、ドメイン購入、課金、広告やアフィリエイトの申し込み（ユーザーの指示があるときだけ）。
- `git push --force` と履歴の書き換え。
- 1回の実行で記事を2本以上公開すること。
- 画像生成AIのモデルのダウンロード（ユーザーの許可があるときだけ）。

## 8. 週1回（日曜）の振り返り
- Search Console などの数字が取れるようになったら、伸びた記事を確認する。
- 公開済み記事の価格・制度の情報が古くなっていないかを見て、直す。
- 次の1週間のネタを `topics.txt` に5本補充する。
